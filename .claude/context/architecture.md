# Architecture / key decisions

[← Project Context](../PROJECT_CONTEXT.md)

- **Flat skill layout everywhere** (`skills/<skill>/SKILL.md`); OpenCode discovers one dir deep. `.skills-manifest.json` rewritten to flat paths, layer grouping preserved.
- **Skill sources**: `dev`/`sql` ← `mariadb-corporation/mariadb-docs` `agent-skills/` (manifest w/ layers). **No pinned commit** — `sync-skills.sh` defaults to the latest on the upstream default branch (`DEFAULT_REF="main"`), `$1` overrides with a tag/branch/commit; the resolved commit SHA is recorded per plugin in `skills-source.json` (`ref`="main", `commit`=the synced SHA). `contributor` ← private `mariadb-shell` `.claude/skills/` (needs `GH_TOKEN`, skips gracefully without). `additional-skills/` (this repo's own) is grouped into topic subfolders — `sql/`, `rest/`, `schema-management/` — vendored flat into a single `additional` manifest layer. `sync-skills.sh` selects per plugin via `ADDITIONAL_SUBDIRS=(sql rest schema-management)` and include keys `additional-<subfolder>` (or bare `additional`=all): dev (empty include list) gets all subfolders; `sql` gets only `sql/` via `SQL_INCLUDE_LAYERS=(granular-statements granular-functions topical additional-sql)`. So `rest/` and `schema-management/` are dev-only.
- **REST skills mirror the MySQL REST Service DDL verbatim** (it's a fork). Branding decisions (user-confirmed): keep upstream identifiers `mysql_rest_service_metadata` + roles `mysql_rest_service_*`; rebrand serving component to **"REST Daemon"** and admin tool to **`mariadb-shell`**. Source docs: `/Users/mzinner/git/mariadb-shell-plugins/mrs_plugin/docs/sections/{sql,devGuide}/*`.
- **MSM (Schema Management) skills** teach the schema lifecycle (create → develop → release → deploy) as an overview + 4 focused skills. Source: `/Users/mzinner/git/mariadb-shell-plugins/{msm_plugin/lib/management.py,mcp_plugin/lib/msm_functions.py}` + `msm_plugin/templates/`.
- **Tier-1 static contract** (each SKILL.md): frontmatter `name` == dir; `description` has "Use when" (≥20 chars); balanced ``` fences; any backticked `mariadb-*`/`mysql-*` under a `## See Also` heading must resolve to a real skill.
- **e2e tests (Tier 4, opt-in `-m e2e`, claude-only)**: each drives the real `claude` CLI **once** in a module-scoped `workflow` fixture, then asserts side effects in **6 separate `test_stepN_*` tests** (runnable individually via `pytest -k stepN`). Two files: `test_e2e_claude.py` (REST) and `test_e2e_msm_claude.py` (MSM).
- **REST e2e** (`test_e2e_claude.py`): spins up a real sandbox; sandbox teardown lives in the fixture `finally` so it always runs (even on timeout). `SHOW REST` are mariadb-shell DDL extensions → run via the MCP server (`_rest_via_show`, discovers the SQL tool from `tools/list` at runtime), with a `mysql_rest_service_metadata` PyMySQL query fallback (`_rest_via_metadata`).
- **MSM e2e** (`test_e2e_msm_claude.py`): **no DB/sandbox** — `msm.prepare_release`/`generate_deployment_script` are pure on-disk ops, so every check is a file. Drives claude through **two releases** (v1.0.0 → develop → v1.1.0) and asserts the *right sections* were used (tables in create-140 / update-240, views in 150 / 250), the **update script was filled** (comments stripped so the empty template can't pass), and the v1.1.0 deployment script composes **all** objects. Hermetic: points `MYSQLSH_USER_CONFIG_HOME` at a throwaway dir and pre-seeds its `settings.json` allow-list with the project dir (no touching real `~/.mysqlsh`, no path-trust elicitation). Section split via `_sections()` on `^-- MSM Section NNN:` banners.
- `mariadb-shell` == MySQL Shell fork (`mysqlsh`); sandboxes in `~/mysql-sandboxes/<port>/`. MCP tools: `sandbox.deploy/start/stop/kill/delete`, `db.connect/execute_sql/execute_sql_script/close`, `msm.*`.
- **Pi (pi.dev) plugin** (`pi/dev-plugin/` + **repo-root `package.json`**): a pi *extension*, not a marketplace plugin. pi has no marketplace file — a package is any dir with a `package.json` `pi` field (`extensions`/`skills`/`prompts`/`themes`), installed via `pi install <path|npm:…|git:…>`. **The manifest is the repo-root `package.json`** (its `pi` field points into `pi/dev-plugin/`: `extensions:["./pi/dev-plugin/src/index.ts"]`, `skills:["./pi/dev-plugin/skills"]` — the skills **root**, NOT a `/*` glob: pi discovers dirs containing `SKILL.md` recursively) so the whole repo installs as one package via `pi install git:github.com/mariadb/ai-plugins` (the install-facing org is **`mariadb`** — a tracking fork; `mariadb-corporation/ai-plugins` stays the source of truth and is still what non-install references, e.g. `additional-skills/README.md` and the `homepage`/`repository` fields, point at). Extension = a default-export factory `export default function(pi: ExtensionAPI){…}` in `pi/dev-plugin/src/index.ts` (loaded by jiti, TS-no-build); its own paths resolve from `import.meta.url` so they're independent of where the manifest sits. pi has **no built-in MCP**: the community `pi-mcp-adapter` (declared as an npm `dependency`) is what connects pi to MCP servers via one token-cheap `mcp` proxy tool, reading a server list from `mcp.json`. Our `scripts/setup-pi-mcp.sh` merges the `mariadb` launcher entry (`lifecycle: "lazy"`) into that config (global `~/.config/mcp/mcp.json` default; `--project`→`./.mcp.json`; `--config PATH`). The extension exposes it as `/mariadb-mcp-setup` and hints at session start when the server isn't configured. Skills vendored flat like the other dev plugins (`pi/dev-plugin` added to `sync-skills.sh` `TARGET_PLUGINS`). No pi test suite yet; the existing static suites only scan their own harness dir, so pi is invisible to them.
- **Codex — five facts that shaped the plugin** (all verified against a clean `CODEX_HOME`, not inferred; established on 0.147, **facts 1-4 re-verified on 0.151.0**):
  1. Marketplace discovery reads **`.agents/plugins/marketplace.json`**, falls back to `.claude-plugin/marketplace.json`, and **never reads `.codex-plugin/marketplace.json`** (22 vs 1 vs 0 references in the binary). Without an `.agents/` file, `codex plugin add dev@mariadb` from this repo installed **`claude/dev-plugin`** — which is the state the user's own `~/.codex` was in. The repo now ships `.agents/plugins/marketplace.json`, and **`.codex-plugin/marketplace.json` was deleted** — verified unread (discovery still resolves all three plugins without it), and keeping a second copy of the same three entries only invites drift. **The per-plugin `codex/*/.codex-plugin/plugin.json` files stay**: codex does read those (27 refs), and without one the install degrades to version `local` with a `dev/local` cache dir.
  2. A plugin's `.mcp.json` must use the camelCase key **`mcpServers`**; a `mcp_servers` key registers **nothing at all**, silently.
  3. The only plugin-root placeholder Codex knows is **`${CLAUDE_PLUGIN_ROOT}`** — there is no `CODEX_PLUGIN_ROOT` string in the binary.
  4. **Codex expands nothing when it spawns a plugin's MCP server.** It execs the stored `command` verbatim, so *any* placeholder fails: `MCP startup failed: No such file or directory (os error 2)`. Re-measured on 0.151.0: still true, and `cwd: "."` does **not** rescue a placeholder.
  5. **But Codex DOES resolve a relative `cwd` against the plugin root, and a relative `command` from there** — so a plugin CAN self-register a working server, which is what `wip/CODEX-MCP-FIX` does. `codex mcp get` shows the stored `cwd` resolved to `…/plugins/cache/<mkt>/<plugin>/<version>/.`. Both halves are required: relative command + no `cwd` fails, placeholder + `cwd` fails. The command must be **extensionless** to serve every OS, per `codex-rs/rmcp-client/src/program_resolver.rs`: on Unix `resolve()` returns the name unchanged and the kernel uses the shebang; on Windows it goes through `which::which_in(program, PATH, cwd)`, which walks `%PATHEXT%` onto the `.cmd`. The extensionless file does **not** shadow the `.cmd` on Windows because `which`'s checker tests an extensionless candidate with `GetBinaryType()`, which rejects a text file (`which` 8.0.0 `checker.rs` + `finder.rs`; the extensionless candidate is yielded *first*, then rejected). **Confirmed on real Windows 11 ARM64 (VM `dev@192.168.10.103`, codex-cli 0.151.0)** with a marker probe: both files present, only the `.cmd` wrote its marker — the extensionless file never executed. Codex's own log is explicit: `program_resolver: Resolved "./scripts/mariadb-mcp-launcher" to "...\26.8.0\.\scripts\mariadb-mcp-launcher.cmd"`. **Full Windows handshake achieved** once the shell was fixed, and a `db.list_connections` tool call reached the server and returned a response. Two shell-side (NOT plugin) Windows findings from that VM: (1) `mariadb-shell` 26.8.0 Win64/ARM64 shipped **without pywin32** — `ModuleNotFoundError: No module named 'pywintypes'` killed the MCP server; reproduced by invoking the shell directly with no Codex/plugin, and **fixed by installing pywin32** into the shell's bundled Python (`<install>/lib/Python3.14/Lib/site-packages/`), which was the only missing dependency. **STILL NOT FIXED in `mariadb-shell` 26.8.1** — tested, do not assume otherwise: a from-scratch install of `mariadb-shell-26.8.1-windows-arm-64bit.tar.gz` (checksum-verified by `install.ps1`, reports `Ver 26.8.1 for Win64 on ARM64`) fails with the same `ModuleNotFoundError: No module named 'pywintypes'`, and **both** Windows 26.8.1 packages (arm *and* x86) contain **zero** pywin32 entries under `site-packages/`, so it is not an arch-specific packaging miss. `mariadb-shell --version` works fine; it is the MCP server path that needs pywin32. So **Windows still needs a manual `pip install pywin32` into the bundled Python**, and the plugins' one-step install is only truly one step on macOS/Linux until the shell packages it. (2) **Testing Windows over SSH distorts the credential helper.** Tools that read secrets fail with `Cannot list secrets, current credential helper is invalid` in an SSH session, because the Windows credential store needs an interactive desktop logon; run directly on the machine and it works (user-confirmed). So an SSH session is fine for verifying process/MCP wiring, but **not** for judging anything that touches stored credentials — don't file that as a bug from an SSH run. Upstream issues, all **open**: openai/codex **#19582** (exact match, same workaround), **#22842**, **#19372**.
- **Codex e2e (Tier 4, new)** — `codex/dev-plugin-test/{test_e2e_codex.py,test_e2e_msm_codex.py}` + `lib/codex_cli.py`, mirroring the claude pair: one `codex exec --json` per module in a module-scoped fixture, then `test_stepN_*` assertions. Codex specifics: skills arrive **only via an installed plugin** (no project-dir discovery), so the fixtures install from `REPO_ROOT` into a throwaway `CODEX_HOME` with the real one's `auth.json` copied in; **`--dangerously-bypass-approvals-and-sandbox` is mandatory** (otherwise every MCP call is auto-cancelled with "user cancelled MCP tool call"); evidence comes from JSONL `item.completed` events with `item.type == "mcp_tool_call"` (`server`/`tool`/`status`); and the injected launcher is a **wrapper that touches a marker then execs the real one**, so "a mariadb server answered" is upgraded to "*this plugin's* launcher was the process Codex spawned".
- **Launcher** — `mariadb-mcp-launcher.sh`/`.cmd`, 14 byte-identical copies (7 `.sh` + 7 `.cmd`; opencode's were shipped `*_disabled` and are **enabled since `wip/mcpLauncherUpdate`**), all propagated by `cp` from `claude/dev-plugin/scripts/`:
  - **Resolution order**: `$MARIADB_SHELL_BIN` → a `mariadb-shell` on `PATH` meeting the gate → a local install at `$MARIADB_SHELL_BINDIR/mariadb-shell` (default `~/.local/bin`, Windows `%LOCALAPPDATA%\Programs\mariadb-shell\bin\mariadb-shell.cmd`) → fetch+run `install.sh`/`install.ps1` from `raw.githubusercontent.com/<repo>/main/`, then launch what it installed. **No asset naming anywhere in the launcher** — that's the whole point; the installer reads the asset list from the release's own `SHA256SUMS` and matches OS/CPU/glibc.
  - **`MARIADB_SHELL_VERSION` = minimum** (default `26.9.1`), compared field-by-field numerically with `10#` base forcing (`version_ge`): `26.10.0`, `26.100.0`, `27.3.0`, `26.08.1` all pass a `26.8.0` gate; missing fields count as 0 (`26.8` passes). Windows uses `[version]$a -ge [version]$b` in PowerShell — same semantics, but stricter on two-component (`26.8` < `26.8.0`) and single-component (`27` throws → "unusable") reports, which real releases never produce.
  - **Version parse is anchored on `Ver`** (`ver\s+N(.N)+` first, bare numeric only as fallback), because the version line starts with the binary path, which may itself carry digits.
  - **stdout is sacred** (it *is* the MCP transport): every launcher message and all installer output is redirected to stderr. Verified 0 bytes on stdout across a real install.
  - **Token** resolved in the launcher too (`MARIADB_SHELL_TOKEN` → `GH_TOKEN` → `GITHUB_TOKEN` → `gh auth token`), because fetching the installer from the private repo needs credentials as well; exported under the name the installer reads.
  - **Prerelease: automatic fallback** (was opt-in until `wip/mcpLauncherUpdate`). The install tries a **stable** release first and retries with `--pre-release` when there is none — so nothing has to be set while `mariadb-shell` publishes only prereleases. `MARIADB_SHELL_PRERELEASE=1` still skips straight to a prerelease (one fewer round trip), `=0` refuses the fallback and keeps the install stable-only. The `.cmd` does the same through `install.ps1`'s env var (`goto install_stable_first` → retry with the var set).
  - **It does NOT track the latest release.** `MARIADB_SHELL_VERSION` is a floor for *accepting* what is already on disk, never a trigger to look for something newer: a `PATH` binary or a local install at-or-above the floor is used **with no network access at all**, so a machine can sit on 26.8.0 forever after 26.9.0 ships. A download happens only when nothing meets the floor, and then it takes the newest release (subject to `MARIADB_SHELL_TAG`, and to `install.sh` picking the newest package the platform's glibc/macOS version can run). **Corollary: a floor set above the newest published release costs a fetch on every server start** — the gate rejects the local copy, the installer re-fetches the same version, and the launcher warns it is still below the floor and starts it anyway (verified). Upgrade by raising the floor with `scripts/set-mariadb-shell-version.sh`, by deleting the managed install, or by running `install.sh` directly.
  - **Fallback**: if the install fails but a binary exists at the target anyway (a concurrent launcher won the race), it is used with a warning; a below-gate version warns rather than refusing to start.
  - **Git-Bash/MSYS**: the `.sh` looks at the `%LOCALAPPDATA%` shim and, since `install.sh` refuses Windows, points at the `.cmd` launcher / `install.ps1` instead of failing obscurely.
- **Pi test suite (`pi/dev-plugin-tests/`, new)** — the 4th suite, so `run_tests.py` now discovers claude/codex/opencode/pi. Tiers: `static` (**611** = the 602 shared + **9 pi-specific**), `db` (**20** since the `db.connect` coverage; self-deployed sandbox), `e2e` (6). **No `eval` tier**: pi has no SDK of its own to prompt, so driving the `pi` binary *is* the behavioural test. The 9 pi-specific static tests guard the wiring that has actually broken here: repo-root `package.json` `pi` field present with resolvable paths, the skills entry pointing at the skills **root** and not a glob, `skills/` holding only skill dirs + the two manifests (the loader constraint that forced two reverts), `pi-mcp-adapter` declared, `src/index.ts` having a default export, and the three shipped scripts present + executable. Its `lib/` is the usual copies (`skills.py`, `mcp_stdio.py`, `sandbox.py`) plus **`lib/pi_cli.py`** for the e2e.
  - **e2e wiring**: temp project → `pi install -l --approve <REPO_ROOT>` (project-local, so nothing lands in the user's pi config) → one `pi -p --approve --no-session --mode json` run. Steps: skills reached the model / `notes-app.sql` written / it carries the skill's Start Block, plus two model-free checks that `setup-pi-mcp.sh` registers `mariadb` at the plugin's launcher with `lifecycle: "lazy"` and is idempotent + preserves other servers. **No MCP tool-call assertions** — pi's MCP comes from the separately installed `pi-mcp-adapter`.
- **DevHub (`docs/`)** — the user-facing docs site, GitHub Pages' own Jekyll from `main` + `/docs`. **No build step, no theme gem, no plugins beyond the Pages allow-list** (`jekyll-seo-tag`, `jekyll-sitemap`), so what GitHub builds is what the folder contains. Tutorials are a Jekyll collection (`docs/_tutorials/`, filename = URL slug, front matter drives the card/filters/pager). **Two of its data sources are generated, not hand-maintained**: `docs/_data/skills.yml` *and* the `skill_count` key in `docs/_config.yml`, both by `docs/regenerate-skills-data.py` from the vendored manifests — and **`sync-skills.sh` runs that generator as its final step**, so the published catalog and counts cannot drift from what ships. That dependency is deliberately **soft** (`command -v python3`): every plugin is already vendored and correct by then, so a machine without python3 warns instead of failing a sync that did all its work. `tool_count`, `shell_floor` and `mariadb_baseline` are still hand-maintained — nothing derives them. `docs/serve.sh` is the local preview (`npm run docs{,:open,:build,:skills}` in the root `package.json`, so they surface in editor script runners). Visual design is a port of `devhub.gridgain.com`'s layout with **its palette copied verbatim** (all 61 light + 42 dark `--ch-*` tokens, the clamps, shadows and hero gradient), except `--ch-section-md` which is cut ~29% for our less dense sections. Code blocks use the **One Dark** prism palette the reference configures as *both* `theme` and `darkTheme`, so they are dark on a light page too; inline code stays light.
- **The DevHub points at the `mariadb` org on purpose, and this is NOT a contradiction of the "source of truth" rule.** `docs/_config.yml` sets `repo: https://github.com/mariadb/ai-plugins`, so its GitHub / Issues / Contributing links go to the fork. **It now serves from the custom domain `ai-plugins.mariadb.com`** (`docs/CNAME`, and `baseurl` emptied so paths are top-level, `d714648`/`39b3c95`) — but `url:` was never moved off `https://mariadb.github.io`, so the emitted canonical tags, `og:url` and `sitemap.xml` still name the old host (verified in the build). See [next steps](next-steps.md). That is the intended workflow: **community issues and PRs are filed on `mariadb/ai-plugins`, then taken in by hand and landed on `mariadb-corporation/ai-plugins`** (which is what the #9 / #7 transfers were). The fork is the community-facing front door; `origin` stays the source of truth and is still where *our* PRs are opened.
- **The DevHub's button and hero treatments are PORTS of mariadb.com, taken from its live stylesheet, not reimplementations.** `app.beedb9.css` (linked from `https://mariadb.com/`) is the source; `--btn-sublime-gradient` was already copied verbatim from it, and `.btn--primary` is now its `btn-deep-ocean btn-outline-gradient` pair (used together 14× on that homepage). **Only colour, gradient and hover/focus/active behaviour are imported** — radius, padding, type and the 1px hover lift stay ours, and `.btn--primary`'s padding gives back exactly the 3px its ring costs so the button measures what it did before. Re-check against that file if the brand look ever moves.
- **The hero code panels are sized by the PANEL, not the viewport, so their responsive rules are container queries.** `.hero-panel` carries `container-type: inline-size`; `.hero-panel__body`'s inset drops to 0 below 480px of panel. This is not a stylistic preference — see the gotcha: panel width is not monotonic in viewport width.
- **Keep `skills/` to ONLY skill dirs + `.skills-manifest.json` + `skills-source.json` — no other files/dirs.** Two things bit us here: (1) the former `skills/topical/` attribution *dir* (`LICENSE`+`VENDORED.md`, no `SKILL.md`) made pi's loader choke ("description is required") → **removed from all plugins**, `sync-skills.sh` no longer emits it (dropped entirely per user; READMEs point at upstream `agent-skills/topical` for MIT terms). (2) A `skills/README.md` note was then tried (copied in by `sync-skills.sh`) — a fixture `pi install -l` looked clean, but **the user reported it still causes loader issues, so it was reverted too**: the copy logic is gone from `sync-skills.sh` and no `skills/README.md` is shipped. Sources/licensing now lives ONLY in `additional-skills/README.md`, and every plugin's top-level README License section links to it via `../../additional-skills/README.md`. The topical *layer* (the skills themselves) is unaffected throughout.
