# Gotchas / things not to repeat

[← Project Context](../PROJECT_CONTEXT.md)

- **A negative-`z-index` pseudo-element paints ABOVE its parent's background only if the parent establishes a stacking context** — otherwise it drops into the nearest ancestor's negative layer and the parent's own background, painted later, covers it. Two live consequences in `style.css`: `.btn--primary` needs `isolation: isolate` for its `::before` fill overlay to sit above the gradient and below the label; and **`container-type` must NOT go on `.hero__card`** — its layout containment would make the card a stacking context and its `::before` bloom, deliberately behind the card at `z-index: -1`, would start painting over it. The container went on `.hero-panel`, which already has `z-index: 1` and holds nothing absolutely positioned.
- **`background-image` is not animatable, so a two-layer background swap always snaps.** mariadb.com's `btn-outline-gradient` hover does exactly that. For a crossfade the moving part has to be something that *is* animatable — here an overlay's `opacity`, with the gradient left in place underneath.
- **Don't copy a Bootstrap button variant's hover/active FILLS into a gradient-outline button — they are invisible there.** `.btn-deep-ocean`'s `#0b1e26`/`#0b2029` are applied as `background-color`, which paints *underneath* the opaque gradient `background-image`; they never show while the outline class is on. Copying them yields dead tokens that look load-bearing.
- **Panel width is NOT monotonic in viewport width, so "the element is narrow" cannot be expressed as a media query.** The hero card is 679px wide inside a 768px viewport but only 361px at 901px, where the hero splits into two columns — so the code samples are clipped on phones *and* across 901–1100px, while a `max-width: 500px` media query would have caught only the phones. Measure the element and use a container query.
- **An absolutely positioned overlay inside a scroll container scrolls away with the content.** A "there's more →" marker must live on a box that does not scroll: either an ancestor, or — as here — move `overflow-x` down onto the `<pre>` so the panel body itself stays still and can carry the marker.
- **`docs/serve.sh --build` wipes `docs/_site` before regenerating**, so any probe/harness file dropped in there vanishes on the next build. Re-create harnesses after each build, and never keep anything of value in `_site` (it is gitignored, which hides the loss).
- **Headless Chrome will not reliably fire `scroll` events for an iframe parked offscreen, and `requestAnimationFrame` may never run under `--virtual-time-budget`.** A scroll-handler test written that way reports whatever the initial state was — it showed a marker "failing to clear" that clears correctly in a real browser, and the same probe gave two different answers on two runs. Drive the handler by dispatching the event yourself (`el.dispatchEvent(new Event('scroll'))`) and assert on the resulting class/computed style; that part is deterministic.
- **An `EXIT` trap never fires after `exec`.** `serve.sh` first wrote a temp config, trapped its cleanup, then `exec`'d Jekyll — leaking the file on every single run. If a script must clean up, it cannot `exec` its final command; run it as a child and forward the status.
- **Jekyll picks its config parser from the file EXTENSION and silently ignores anything that is not `.yml`/`.yaml`.** A `--config` pointed at a `mktemp` file with no extension warns `Error reading configuration. Using defaults` and **builds on with the wrong `baseurl`** — a broken site that looks like a working one. `mktemp -t` cannot portably produce a name ending in `.yml`, so make the *directory* random and the file inside it fixed.
- **`Gem::MissingSpecError` is NOT a `StandardError`.** Its ancestry is `Gem::LoadError < LoadError < ScriptError < Exception`, so `rescue StandardError` (and a bare `rescue`) does not catch it. A gem-presence check written that way is inert: ruby aborts, the status gets discarded, and every gem looks present. Rescue `Gem::LoadError` explicitly.
- **macOS's `/usr/bin/gem` has a gem set unrelated to a Homebrew Ruby's** — it reports zero jekyll gems where the Homebrew one has five. A `PATH` that reaches the gem *bin* directory (so `jekyll` resolves) without reaching `/opt/homebrew/bin` (so `gem` does not) is easy to end up with, and an editor launched from the Dock rather than a shell often has exactly that. **Ask the Ruby that will run the tool** — read the shim's shebang — not whatever `gem` is first on `PATH`. This was reported as "npm run docs says my installed gems are missing".
- **`[hidden]` comes from the UA stylesheet, so ANY author `display` rule beats it.** `.card { display: flex }` silently defeated `el.hidden = true` and the DevHub's tutorial filters did nothing while the buttons' pressed state updated correctly — it read as a JS bug and was CSS. Ship the global `[hidden] { display: none !important; }` a reset would normally carry; the `!important` is load-bearing, since without it every future component `display` rule re-breaks `hidden` for that component. One deliberate exception needs `!important` of its own: the navbar links stay visible above 901px although the mobile toggle leaves the attribute set.
- **Chrome headless has a MINIMUM window width** (~500px), so `--window-size=390,…` lays the page out wider and merely *crops* the screenshot. Narrow-viewport screenshots therefore look broken when they are fine, and hide real overflow when they are not. Measure `documentElement.scrollWidth > clientWidth` inside a sized `<iframe>` instead — that is what caught the genuine overflows (grid children defaulting to `min-width: auto`, and wide tables).
- **`sandbox.deploy` registers a connection; `db.connect` needs no password.** It calls `config.store_connection("root@127.0.0.1:<port>", password)`, `db.list_connections` is derived from those *secrets* (not a registry of its own), and `db.connect` checks its argument against that list. Consequences: the registration is only visible through the config home holding the secret store, and an **unreadable secret store makes every connection look unconfigured** — which is exactly how a working deploy misreads as a broken one (seen on Windows over SSH). Covered by `test_db_connect.py` in all four suites.
- **Don't judge credential-touching behaviour from an SSH session on Windows.** The Windows credential store needs an interactive desktop logon, so over SSH the shell's secret-reading tools fail with `Cannot list secrets, current credential helper is invalid`; run directly on the machine and they work (user-confirmed on the `dev@192.168.10.103` VM). SSH is fine for process/MCP-wiring checks, which is what the Codex launcher verification needed.
- **`mariadb-shell` is PUBLIC now** (was private; re-verified anonymously 2026-09-01: `api/repos` 200 `"visibility": "public"`, the tarball 200, `raw.githubusercontent.com/.../install.sh` 200). So neither `sync-skills.sh` nor the launcher needs a token any more — `sync-skills.sh` no longer skips the contributor plugins without one (verified: with `GH_TOKEN`/`GITHUB_TOKEN` unset *and* a `gh` that cannot authenticate, all 3 contributor plugins sync and the output is byte-identical to the authenticated run). A token is still passed when available, for the API rate limit and in case it goes private again. **The old note conflated two causes — don't repeat that:** anonymous `releases/latest` still answers **404**, but that is purely because every release is a prerelease and `releases/latest` excludes those, NOT privacy. `releases` (the list) answers 200 and shows `v26.9.1`, `v26.9.0`, `v26.8.1` and `v26.8.0`, all prerelease.
- **Every published release is still flagged prerelease** — `v26.9.1` (2026-09-07), `v26.9.0` (2026-09-02), `v26.8.1` (2026-09-01) and `v26.8.0` (2026-08-13), verified with `gh release list` (re-checked 2026-09-08, when `v26.9.1` showed up). So `releases/latest` still resolves to nothing and an unattended install still depends on the launcher's prerelease fallback (or `MARIADB_SHELL_PRERELEASE=1`). 26.8.1 assets: `install.sh`, `install.ps1`, `SHA256SUMS`, and `mariadb-shell-26.8.1-{linux-glibc2.34-arm,linux-glibc2.34-x86,macos15-x86,macos26-arm,windows-arm,windows-x86}-64bit.tar.gz` — note the macOS matrix is **not** the full cross product: macos15 is x86-only and macos26 arm-only. **Package versions are 26.x; the local source build still reports `Ver 9.7.0`** — so with the gate at 26.9.1 the local build on PATH is rejected; use `MARIADB_SHELL_BIN` for it (which is what the e2e tier already does).
- **`gh release create` cannot combine `--notes-from-tag` with `--repo`** (gh 2.97): the annotation is read from the *local* clone, and `--repo` takes it out of that context, so the pair is rejected outright. With more than one remote and no `gh repo set-default`, `--repo` is unavoidable — so extract the message yourself (`git tag -l --format='%(contents:body)' <tag>` → `--notes-file`), which also guarantees two repos get byte-identical notes. Always pass **`--verify-tag`**: without it a typo'd tag name is silently *created* as a lightweight tag off the default branch instead of failing.
- **Installer targets**: `install.sh` → unpacks to `~/.local/share/mariadb-shell/<ver>/`, symlinks `~/.local/bin/{mariadb-shell,msh}`, keeps only the 2 newest versions, and **only prints a PATH hint — never edits a shell profile**. `install.ps1` → `%LOCALAPPDATA%\Programs\mariadb-shell\`, `bin\*.cmd` shims written with `%~dp0`-relative paths. Both are overridable with `MARIADB_SHELL_PREFIX`/`_BINDIR`; `install.sh` needs curl+tar+awk, and jq or python3 only on the API path (token or `--pre-release`).
- **Testing a resolution chain: measure the branch, not the outcome.** A first probe keyed on "did the shell get launched" reported ACCEPTED for *every* version, because a rejected binary is still launched by the install-failure fallback. Assert on the launcher's own stderr line instead. Stub binaries (`--version` prints a fake `Ver x.y.z`, anything else echoes a marker) cover the whole table cheaply.
- **pi does NOT load a dependency's pi resources.** Per pi 0.84.1 `docs/packages.md`: resources load only from packages listed in settings, and *"other pi packages must be bundled in your tarball. Add them to `dependencies` **and** `bundledDependencies`, then reference their resources through `node_modules/` paths."* Our root `package.json` does neither, so **`pi install npm:pi-mcp-adapter` is a required separate step** — the `dependencies` entry only version-constrains the module. Also: `pi install <path>` writes just that path to `.pi/settings.json` `packages` and runs **no** `npm install` (that happens for `npm:`/`git:` sources only). Useful for testing: `pi install -l --approve <path>` in a throwaway dir touches nothing global; `pi list` was empty before/after.
- **Editing `additional-skills/` without re-running `scripts/sync-skills.sh` silently ships stale text** — it bit us for 4 days (`mariadb-schema-create-script`, 7 plugins). Nothing else notices: the manifest still matches disk and the stale copy still parses. Now caught by `test_additional_skill_matches_its_source`.
- **`sync-skills.sh` at latest `main` can bring unrelated upstream churn** — the 2026-08-14 run touched 432 files mostly because upstream added a copyright footer to every skill. Read `git diff --shortstat` + one sample diff before assuming a sync means content revisions.
- **pi ignores project-local files unless the run passes `--approve`/`-a`.** `pi install -l` writes `.pi/settings.json` and reports success, but without `-a` at run time the package is configured and never loaded — the skills are simply absent with no error. Also: **`pi list` reads only the *user* settings**, so it prints "No packages installed" whether or not a project-local package is live; it is not a check that anything loaded.
- **pi exposes no skill/package data in its event stream** (`--mode json` yields session/agent/turn/message events only), and the extension's `session_start` notify does not surface in `-p` mode. So there is no deterministic in-band proof that skills loaded: the honest evidence is behavioural (the generated script carrying the skill's Start Block), plus matching the assistant text against the **real vendored names** via `skills.skill_names()`.
- **`env` options must precede the assignments.** `env FOO=1 -u BAR cmd` treats `-u` as the *command*, exits 127 having run nothing — and a check written that way ("0 files installed, as expected") proves nothing. Cost a wrong conclusion about the `MARIADB_SHELL_PRERELEASE=0` path until the exit code was actually read.
- **Don't assert model obedience and call it wiring.** Twice now a test demanded the model produce a fixed shape (codex: `msm.*` tools only; pi: "list four skill names") and went red while the plugin was fine — the codex MSM artifacts were correct via the CLI, and pi's weak local model named one skill while writing a correct script. Assert the side effect the plugin controls; keep preference checks separate.
- **pi's provider here is a LOCAL ollama model** (`qwen3.6:35b-a3b-coding-mxfp8`), so the pi e2e is free but weak on long instructions — and `pi auth check --provider <x>` reports `not_ready` even when runs succeed, which is why the gate gets its answer from a trivial round trip instead of inspecting credentials.
- **Codex spawns MCP servers with a FILTERED environment.** An exported `MARIADB_SHELL_USER_CONFIG_HOME` does not reach the server, so the shell falls back to the real `~/.mariadb-shell` and its allow-list — and the `msm.*` tools then reject each run's throwaway project dir, after which the model quietly falls back to the `mariadb-shell` CLI (same `msm` plugin, no path guard) and produces *correct artifacts with zero MCP calls*. Declare env in the server's own entry: `-c 'mcp_servers.mariadb.env={MARIADB_SHELL_USER_CONFIG_HOME="…", …}'`. This one masqueraded as three different bugs (path spellings, stdin handling, "model whim") before the real cause surfaced — the tell was the model saying the dir was rejected "despite it appearing in settings.json", plus a **stale test path from an earlier run still sitting in the real `~/.mariadb-shell/plugin_data/mcp_plugin/settings.json`** (which is why the very first MSM run passed).
- **`subprocess.run` on `codex exec` MUST pass `stdin=subprocess.DEVNULL`** — codex reads a piped stdin as extra prompt input and blocks forever on one that never EOFs. Symptom: a run that hangs to the timeout with an *empty* event stream (cost a 7-minute diagnostic).
- **Seed the MCP allow-list with BOTH macOS path spellings.** `$TMPDIR` yields `/var/folders/...` while `Path.resolve()` yields `/private/var/folders/...`, and the path guard compares strings — seed one and the tier is flaky. Seen for real: the MSM e2e passed alone, then failed with the model reporting "the workspace path ... is not registered in its allowed-paths setup", and it **fell back to running the shell CLI directly**, producing genuine MSM artifacts with no MCP call at all. `lib/codex_cli.py::_path_spellings` now seeds every variant. (This is also why the MSM module's step6 — "completed `msm.*` calls in the event stream" — matters: steps 1-5 can be satisfied by a CLI fallback.)
- **Batch files must be CRLF** — see `.gitattributes`. Also keep them ASCII (em dashes in `rem` lines were converted to `--`). Note git stores the blobs as **LF** (`text eol=crlf` normalizes on commit, converts on checkout) — verified with a fresh clone, which yields CRLF `.cmd` and LF `.sh`. Don't "fix" the LF blob.
- **A licence header in a `.cmd` must go AFTER `@echo off`** — command echo is on until it runs, so `rem` lines above it print to **stdout**, which for the launchers is the MCP JSON-RPC transport. Same reasoning as the stdout rule above.
- **Check the branch before committing.** The user moved the working tree from `wip/updateMcpLauncher` to `main` mid-session (`git checkout main` + `git pull` → fast-forward to *rebased* copies of the two launcher commits, i.e. **different SHAs**: `735f74a`/`b00fbc3` on main vs `394d599`/`fb549a6` on the wip branch). The header commit therefore landed on `main`. `git diff wip/updateMcpLauncher main` confirmed the only delta was the header commit's 47 files / 696 insertions, so nothing was lost — but read `git status -sb` before `git commit` rather than assuming the branch from earlier in the session.

- **REST DDL over MCP root cause (user FIXED in `mysql-shell-plugins/mrs_plugin/lib/general.py`)**: REST metadata deploy chose its management session via `"shell.Object" in str(type(session))` → `open_session()` (no-arg = duplicate the GLOBAL session), which raises **"An open session is required when duplicating sessions"** when there's no global session (headless/MCP). Interactive worked only because a global session existed. Empirically: MCP session type = `<class 'shell.Object'>`, headless global session = `None`, and `shell.Object` has no `.connection_options` (so the else-branch fallback also failed; `get_uri()` strips the password → prompt hang).
- **MSM deployment composition:** sections **140/240/170/270** become **stored-procedure bodies** → plain `;`-terminated, NO `DELIMITER`, dynamic SQL for conditional DDL; sections **130/150/230/250/190/290** are top-level with `DELIMITER %%`. Order: `prepare_release` → **fill update script (240/250/270)** → `generate_deployment_script` → `deploy_schema` (generating before filling the update script yields a script that creates fresh but can't upgrade older installs).
- **MSM SOURCE breakout:** `SOURCE './sections/x.sql'[start:end];` uses **character-offset** slices to strip each file's own copyright header/footer (`[53:]`, `[663:-115]`, `[:N]`); relative to `development/`; inlined at `prepare_release` (dev-time only).
- **bash 3.2 (macOS) + `set -u`:** guard empty-array expansion (`[ "${#arr[@]}" -gt 0 ]`) — done for `add_subdirs` in `sync-skills.sh`.
- **All the file-touching MCP tools are path-gated** by the server's `settings.json` allow-list (`<config home>/plugin_data/mcp_plugin/settings.json`, key `allowedPaths`); a non-allowed path falls back to an elicitation a headless client can't answer. For the MSM tools that fails the call; for `sandbox.deploy` it **HANGS** — so always pre-seed the allow-list. The `msm` plugin method is `msm.create_new_project_folder` (not `create_project`); `license="GPLv2"` is rejected (no stored license by that name) — omit it or pass custom text.
- **Shell config home — two facts that cost time:** (1) the current build's real one is **`~/.mariadb-shell`**, not `~/.mysqlsh` (log is `mariadb-shell.log`), though **`MYSQLSH_USER_CONFIG_HOME` is still honored** for relocating it (`MARIADB_SHELL_USER_CONFIG_HOME` too — set both). (2) **the shell loads its plugins from the config home**, and on this source build `mcp`/`msm`/`mrs` are symlinks in `~/.mariadb-shell/plugins/` — so relocating it to a bare temp dir kills the MCP server outright (`ERROR: There is no object registered under name 'mcp'`). Isolate it *and* symlink the real one's plugins in (what `lib/sandbox.py` does). Also: the config home dir must already exist, or the shell dies on "Error opening log file".
- `db.execute_sql_script` runs each statement in a **fresh session** → REST grammar needs one continuous session; run REST statements individually via `db.execute_sql` on one connection (claude adapts automatically).
- MCP `db.connect` **no longer** needs a bare uri — **this gotcha is out of date, measured 2026-09-01**: `config.normalize_connection_uri` now folds a `mariadb://`/`mysql://` prefix, host case, the default port and an inline password onto the stored `root@127.0.0.1:PORT` key, so all of those open the connection (verified by `test_db_connect.py`). What is still refused is a uri asking for **more** than was configured — a default schema (`…:PORT/schema`) or an option (`?ssl-mode=REQUIRED`) — deliberately, so a caller is never handed a connection that quietly drops what it asked for. That refusal is still "not a configured connection"; `db.execute_sql_script` rejects file paths outside allowed paths → pass SQL inline.
- Background `... | tee log` reports **tee's** exit (0), not pytest's — always read the pytest summary line.
- Timeouts orphan sandboxes if teardown isn't in a `finally` (leaked 51111/51914 earlier). Clean via MCP `sandbox.stop`+`sandbox.delete` (fallback `sandbox.kill`). All session sandboxes now cleaned (51111, 51914, 52646, e2e's 54042).
- Foreground `sleep` is blocked by the harness; use `run_in_background` / Monitor.
- `see_also_refs()` counts only backticked `mariadb-*`/`mysql-*` under `## See Also`; underscored names like `mysql_rest_service_metadata` don't match (safe).
- Sandbox root password must not be blank (the e2e tier pins `test`, the db tier `skilltest_root`); `sandbox.delete` refuses a running instance, so `sandbox.kill` is the fallback when `stop` fails. Deploy with `ssl: False` to avoid needing openssl.
- **Two shell-plugins checkouts exist**: `~/git/mariadb-shell-plugins` (the **active** one, and what `~/.mariadb-shell/plugins/` symlinks point at) and `~/git/mysql-shell-plugins-old` from before the rename. Same layout; always read/patch the active one. **The rename silently broke the plugin symlinks** (2026-09-01): all three still pointed at the vanished `~/git/mysql-shell-plugins`, so the MCP server died with `ERROR: There is no object registered under name 'mcp'` and the **whole db tier skipped** in every suite — a skip, not a failure, so a run looked fine. `mrs` and `msm` were broken the same way, which would have taken the REST and MSM e2e modules with them. Repaired with `ln -sfn`; if that error appears again, check these symlinks *first*.
